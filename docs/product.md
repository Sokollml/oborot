# Продукт: проблема, гипотезы, MVP

> **Важно.** Всё ниже — **гипотезы** команды. Интервью с предпринимателями и специалистами банка мы ещё не
> проводили; сценарий интервью для их проверки — [interview-guide.md](interview-guide.md). Цифр «из опросов»
> здесь нет и не должно быть, пока интервью не проведены.

## Проблема

Малый бизнес берёт кредит редко и без подготовки. Заявку обычно заполняет собственник или бухгалтер, у которых нет
банковской экспертизы. Гипотеза: основные потери времени и нервов возникают не на самом решении банка, а вокруг него:

- непонятно, какой продукт подходит и сколько придётся платить в месяц;
- анкета требует данных, смысл которых неясен («долговая нагрузка», «ОКВЭД»);
- после отправки заявка «пропадает»: непонятно, что с ней, сколько ждать и нужно ли что-то сделать;
- отказ приходит без объяснения, и непонятно, есть ли смысл подавать снова.

Со стороны банка гипотеза зеркальная: специалист тратит время на сбор данных из разных систем и переписку с клиентом,
а не на само решение; простые заявки без нужды доходят до человека.

**Идея продукта:** цифровой кредитный конвейер, где простые заявки решаются автоматически за минуты,
а сложные приходят специалисту уже с проверками, скорингом и рекомендацией. Клиент на каждом шаге видит
понятный статус и следующий шаг. Одна заявка, два кабинета.

## Гипотезы в формате Jobs To Be Done

Формат: *Когда … , я хочу … , чтобы …* → функция, которая проверяет гипотезу → как поймём, что гипотеза верна.

## MoSCoW

| Приоритет | Что | Почему так |
|---|---|---|
| **Must** | Сквозной путь клиента: подбор → анкета → статус → решение → подпись → выдача | Без этого нечего показывать: ценность продукта — в непрерывном пути, а не в отдельных экранах |
| **Must** | Автоматический конвейер: проверки, скоринг, таблица решений | Главная гипотеза — простые заявки решаются без человека за минуты |
| **Must** | Кабинет специалиста: очередь, карточка, решение с комментарием | «Одна заявка — два кабинета»: сложные случаи должны доходить до человека с готовыми данными |
| **Must** | Статус в реальном времени и «Что дальше» на каждом шаге | Гипотеза К3 — главная боль клиента после отправки |
| **Must** | Надёжность: очередь в БД, повторы, переживает падение воркера, недоступный внешний сервис → специалист | Кредитная заявка не может «потеряться» или зависнуть — это базовое ожидание от банка |
| **Must** | Безопасность: роли, проверка владельца заявки (403), идемпотентность отправки | Минимум, без которого конвейер нельзя показывать как банковский |
| **Should** | Контрпредложение вместо отказа, причины и советы, «Подать заново» | Гипотеза К4: сохранить клиента, которому «почти» одобрили |
| **Should** | Запрос и загрузка документов | Нужен для сценария «средний риск → подтвердить выручку» |
| **Should** | Уведомления в кабинете | Возвращают клиента, когда нужно его действие |
| **Could** | Рекомендация системы для специалиста с кнопкой «подставить» | Ускоряет решение, но специалист справится и без неё |
| **Could** | Пересмотр решения специалистом (изменить предложение, отменить отказ) | Нужно для реальной работы, на демо — дополнительный эффект |
| **Won't (сейчас)** | LLM-помощник, ML-скоринг | Нет данных для обучения; решения должны быть объяснимыми; LLM — только локальный и только опционально |
| **Won't (сейчас)** | Реальные интеграции, ЭП, мобильное приложение, регистрация | Недоступны на хакатоне или не проверяют ключевые гипотезы |

**Почему именно такой MVP.** Мы проверяем одну цепочку: *понятный путь клиента + автоматическое решение простых
случаев + специалист получает только сложные заявки с готовыми данными*. Всё, что не влияет на эту цепочку
(регистрация, реальные интеграции, ML), заменено симуляцией или отложено. Всё, что делает путь непрерывным
и прозрачным (статус в реальном времени, причины решения, надёжность конвейера), — в Must.

## Метрики, которые стоит измерять в пилоте

- Время от входа до отправки заявки; доля брошенных анкет по шагам.
- Доля заявок, решённых автоматически; время до решения (авто / с участием специалиста).
- Время специалиста на одну заявку; доля решений, где специалист не согласился с рекомендацией.
- Доля принятых контрпредложений; доля повторных заявок после отказа.
- Обращения клиентов «что с моей заявкой» (цель — снижение).
